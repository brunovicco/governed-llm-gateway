Working repository name: governed-llm-gateway
Status: Proposed / Architecture Gate

Development harness: codex-python-engineering-harness
Primary coding agent: Codex
Independent reviewer: Claude Code

⸻

1. Project purpose

Build a reusable, provider-neutral LLM execution gateway that selects and invokes the most appropriate authorized model for a workload while preserving:

* deterministic governance boundaries;
* task-aware model selection;
* provider abstraction;
* capability enforcement;
* safe fallback;
* runtime availability handling;
* cost and latency constraints;
* evaluation-driven model ranking;
* OpenTelemetry observability;
* privacy-safe audit evidence;
* explainable routing decisions.

The gateway must become the standard LLM access layer for future projects.

Applications should not need to know:

* provider API keys;
* concrete model identifiers;
* provider-specific APIs;
* fallback ordering;
* model pricing;
* live provider health;
* benchmark scores;
* routing policy implementation.

Applications should declare what they need, not which model to call.

Example conceptual call:

result = await gateway.generate(
    workload="agent.orchestration",
    messages=messages,
    requirements={
        "tool_calling": True,
        "structured_output": True,
        "min_context_tokens": 128_000,
    },
)

The platform decides the authorized model group and concrete deployment.

⸻

2. Core architectural principle

The system must separate three decisions:

Can this workload use this class of model?
                  │
                  ▼
        Policy Model Router
        Policy Decision Point
                  │
            model group
                  │
                  ▼
Which authorized deployment is best right now?
                  │
                  ▼
         Governed LLM Gateway
     Operational Selection + PEP
                  │
        provider + model
                  │
                  ▼
             LLM Provider

The gateway must never override an authorization decision from the Policy Model Router.

It may further restrict the available models.

It may never broaden the authorization.

Invariant:

Gateway allowed set
        ⊆
Policy Router authorized set

3. Relationship with existing repositories

3.1 policy-model-router

Decision

Reuse and evolve. Do not merge into the gateway.

Role:

Policy Decision Point — PDP

Responsibilities:

* workload → logical model-group authorization;
* data-classification constraints;
* risk constraints;
* tool-calling requirement;
* structured-output requirement;
* context ceiling;
* policy cost ceiling;
* policy latency ceiling;
* agent allowlist;
* deterministic explainability;
* policy provenance;
* fail-closed authorization.

It must continue to not perform inference.

Required evolution

The current implementation contains domain-specific closed enums for workloads and model groups.

Before production integration with the gateway, create a new Policy Model Router contract where:

Workload

becomes a validated policy-defined identifier rather than a Python enum.

Example:

classification.simple
extraction.structured
rag.answer
reasoning.complex
security.analysis
code.generate
code.review
agent.orchestration
agent.tool-use
multimodal.analysis

Likewise, logical model groups should be policy-defined.

Example:

fast-small
balanced
reasoning-strong
agentic-strong
multimodal
structured-fast

DataClassification and RiskLevel should remain controlled vocabularies.

Unknown workloads must continue to fail closed.

The existing credit-desk policy should become an example policy rather than the system-wide vocabulary.

Recommended migration:

policy-model-router 0.x
        │
        ▼
generalization ADR
        │
        ▼
policy-model-router 1.0

Do not make the gateway responsible for translating generic workloads into credit-specific ones.

17. Routing algorithm

Routing has two distinct stages.

Stage A — authorization

Performed by policy-model-router.

Input:

workload
risk
data classification
required capabilities
context
cost ceiling
latency ceiling
agent identity

Output:

authorized logical model group
+
decision provenance

No inference.

⸻

Stage B — operational model selection

Performed by the gateway.

Candidates must first satisfy:

belongs to authorized group
provider enabled
deployment enabled
required modality available
tool calling available if required
structured output available if required
context capacity sufficient
provider allowed for environment/data
live circuit breaker not open
deployment healthy enough
cost fits remaining limit

Only eligible deployments are ranked.

⸻

18. Ranking

Initial ranking should be deterministic and explainable.

Example:

score =
    task_quality_score
  + reliability_score
  + latency_score
  + cost_score
  + availability_score

Weights are configured per workload.

Example:

agent.orchestration:
  quality: 0.40
  reliability: 0.25
  latency: 0.15
  cost: 0.10
  availability: 0.10

Do not hard-code rankings such as:

Kimi is always best for agents.

Instead:

benchmark snapshot X
        ↓
task score
        ↓
ranking policy Y
        ↓
routing decision

Both snapshot and ranking policy must be versioned.

23. Fallback safety

Fallback must be treated as an execution-safety problem, not only an availability feature.

Safe example:

request
  ↓
model A
  ↓
HTTP 503 before response
  ↓
model B

Potentially unsafe example:

model A
  ↓
tool call
  ↓
external operation executed
  ↓
switch to model B

Default policy:

transport failure before model output
    → fallback allowed
rate limit before model output
    → fallback allowed
schema failure, no side effect
    → bounded repair/retry allowed
tool call generated but not executed
    → conservative policy
tool side effect executed
    → no cross-provider fallback
opaque reasoning state established
    → no cross-provider continuation unless replay strategy explicitly supports it

Fallback candidate must remain inside the authorized model group.

Never fallback outside policy authorization.

⸻

24. Retry policy

Distinguish:

retry

from:

fallback

Retry:

same deployment

Fallback:

different eligible deployment

Retry only transient failures:

408
429
5xx
network timeout
connection reset

Use bounded exponential backoff with jitter.

Do not retry permanent validation or authorization errors.

  ↓ cooldown
HALF_OPEN

CLOSED

Initial implementation may be per-process.

Later add Redis-backed shared state.

Metrics:

success rate
timeout rate
429 rate
5xx rate
p95 latency
breaker state

27. Structured output

Structured output is a capability, not a prompt convention.

The gateway must distinguish:

provider-native schema enforcement

from:

prompted JSON

They are not equivalent capabilities.

Schema validation happens after provider response even when the provider claims native enforcement.

Invalid output should produce a typed failure.

Optional bounded repair can be added later.

28. Tool calling

Normalize:

ToolDefinition
ToolCall
ToolResult

Provider adapters translate the canonical representation.

The gateway does not execute business tools.

Tool execution remains the responsibility of the agent/application/MCP layer.

Therefore:

gateway
    → chooses/invokes model
agent runtime
    → authorizes and executes tool

This preserves authority boundaries.

50. Definition of success

The project is successful when a new application can declare:

workload="agent.orchestration"

without knowing whether the actual request will execute on:

Kimi
Gemini
DeepSeek
Nemotron
OpenAI
Claude
or another future model

while still being able to answer afterward:

Why was this model authorized?
Why was this deployment selected?
What alternatives were rejected?
Which policy was used?
Which registry was used?
Which benchmark influenced the ranking?
Did fallback happen?
How long did it take?
How many tokens were consumed?
Was the request within its cost budget?
Was the execution permitted for this data classification?
Can the decision be reconstructed later?

That is the central engineering objective of the project.
